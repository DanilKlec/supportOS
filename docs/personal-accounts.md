# Пользователи, роли и разрешения

Пароли и вход остаются в Supabase Auth. Права приложения хранятся в обычных таблицах схемы public и управляются через **Настройки → Пользователи, роли и доступы**.

| Таблица | Назначение |
|---|---|
| supportos_users | Пользователь, почта, имя, статус, версия записи; ID связан с auth.users |
| supportos_roles | Системные и пользовательские роли |
| supportos_permissions | Каталог разрешений функций приложения |
| supportos_user_roles | Несколько ролей одного пользователя, кто и когда назначил |
| supportos_role_permissions | Разрешения каждой роли |
| supportos_access_audit | Кто, когда и что изменил; значения до и после |

Разрешения всех назначенных ролей объединяются. При статусе «Отключён» или «Ожидает доступа» эффективных прав нет. Новые аккаунты Auth автоматически попадают в supportos_users без ролей. Создание через интерфейс добавляет роли после создания аккаунта; если назначение не удалось, аккаунт остаётся без доступа, а интерфейс сообщает об этом.

## Начальные роли

| Роль | Начальные права |
|---|---|
| Support | Бинды, почты сайтов, депозитные бонусы и условия, личные настройки |
| Shift | Рабочие инструменты, правка общих биндов и бонусов, мониторинг и графики, инструкции ИИ |
| QC | Рабочие инструменты, правка общих биндов и бонусов, просмотр мониторинга и журнала |
| Admin | Управление продуктом, пользователями, ролями и разрешениями; без технических настроек |
| Creator | Полный доступ, включая технические настройки и назначение владельцев |

Эти наборы используются только при первом заполнении таблиц. Далее права настраиваются галочками во вкладке «Роли и разрешения». Можно создавать дополнительные роли. Каталог из 13 разрешений соответствует реализованным функциям: добавление новой функции с новым разрешением требует изменения кода и каталога.

## Защита изменений

- Все изменения проверяются в транзакционной функции supportos_rbac_change, доступной только серверу. API передаёт ID, подтверждённый через Supabase Auth, а не ID из формы.
- Нельзя назначить права выше собственных, изменить более привилегированного пользователя или собственную роль/статус. Технические права закреплены за Creator.
- Creator защищён от изменения через формы. Системные роли нельзя удалить; пользовательскую роль можно удалить только после снятия всех назначений.
- Версия записи предотвращает перезапись изменений другого администратора. Изменения сериализуются и повторно проверяют полномочия администратора после блокировки.
- Аудит записывается в той же транзакции. Удаление аккаунта из Auth не удаляет старый аудит.
- Непосредственные операции браузера с таблицами доступа запрещены. Интерфейс получает только нужные данные через защищённые API.

API и RLS читают актуальные таблицы. JWT и app_metadata больше не определяют права приложения. Интерфейс обновляет разрешения каждые 30 секунд и при возврате фокуса; устаревший ответ не перезаписывает более новый. При ошибке проверки интерфейс закрывает доступ, серверные проверки продолжают действовать.

## Миграция и публикация

В проекте exijfprfwmyplggayrpt применена **supabase/rbac.sql** после схемы общих данных. Перенесён существующий аккаунт с прежней ролью Admin, без повышения до Creator. Старые user/supervisor при первоначальном переносе соответствуют Support/Shift. Повтор миграции сохраняет изменённые роли, разрешения и статусы; изменения metadata после переноса не дают доступ.

Для нового проекта используйте **supabase/schema.sql** — полный набор схем общих данных, RBAC и инструкций ИИ. **supabase/access-control.sql** — базовая часть; отдельно повторять её после RBAC нельзя, так как она содержит старую реализацию вспомогательной функции. После неё всегда нужна rbac.sql.

Переменные окружения:

- Клиент: VITE_SUPABASE_URL, VITE_SUPABASE_PUBLISHABLE_KEY.
- Сервер: SUPABASE_URL (или VITE-вариант), SUPABASE_PUBLISHABLE_KEY (или VITE-вариант), SUPABASE_SERVICE_ROLE_KEY. Теперь серверный ключ нужен всем API, проверяющим права.

Изменения интерфейса и API требуют публикации ветки. Таблицы уже созданы в Supabase. Creator существующему аккаунту не назначен: это отдельное повышение доступа, которое ранее было заблокировано автоматической проверкой и ожидает явного подтверждения.

## Данные продукта

Система доступа не переносит локальную базу знаний, бонусы или Excel-графики автоматически. Существующая облачная синхронизация биндов включается через VITE_SUPPORTOS_CLOUD_SYNC=true. Личные снимки и очереди разделены по аккаунтам. Бонусные справочники сохраняют прежний способ хранения.

Раздел AI Knowledge сохраняет общие инструкции и примеры ответов в Supabase; генератор подставляет серверную версию. Это инструкции для модели, а не fine-tuning.

## Проверка защиты

Таблицы доступа, мониторинга и инструкций ИИ закрыты для браузерных ролей; RLS без пользовательских политик на этих серверных таблицах намеренна. Функция supportos_access возвращает только булево право текущего auth.uid(), не принимает чужой ID и не изменяет записи; SECURITY DEFINER нужен для чтения закрытых таблиц прав. [Предупреждение линтера о доступной функции](https://supabase.com/docs/guides/database/database-linter?lint=0029_authenticated_security_definer_function_executable) для неё ожидаемо. В проекте отключена [проверка скомпрометированных паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection); эта настройка Auth не менялась.


## Общие бинды и личные версии

Раздел `/shared-binds` работает напрямую с Supabase и не требует `VITE_SUPPORTOS_CLOUD_SYNC`.
- **Мои ответы**: общие оригиналы с личными версиями пользователя поверх них. «Изменить под себя» создаёт отдельную запись; возврат к общей версии удаляет только персональную копию.
- **Общая база**: создание и редактирование оригиналов с `knowledge.write` (Shift, QC, Admin, Creator по умолчанию).
- **Бинды сотрудников**: поиск по имени/почте, изменение и сброс личных версий с `binds.manage` (Admin и Creator по умолчанию). Право настраивается в редакторе ролей.
Личные версии ссылаются на исходный бинд через `source_bind_id`; обновление оригинала не перезаписывает их. `source_hash` хранит дату исходника для уведомления об обновлении.
Сохранение проверяет ожидаемую дату изменения, а изменение/сброс личной версии атомарно записывается в журнал доступа. Содержимое журнала биндов видно только с `binds.manage` в дополнение к доступу к журналу.
Для существующих установок применить `personal-binds.sql` после `rbac.sql`; полный `schema.sql` уже включает её. Ни старые локальные данные, ни таблицы графиков автоматически не загружаются. Старое локальное рабочее пространство остаётся отдельным от опубликованной общей базы.
