# Supabase Auth, Google и Google Authenticator

SupportOS использует Supabase Auth. На `/login` доступны вход через Google, вход по почте/паролю и регистрация с подтверждением рабочей почты. Кнопки Google во вкладках входа и регистрации содержат цветной значок провайдера. Подключение Google Authenticator (TOTP) добровольное: после входа откройте «Настройки → Безопасность → Включить 2FA», отсканируйте QR-код и подтвердите шестизначный код. Только после успешной проверки 2FA становится активной; затем при каждом входе требуется второй фактор. Новые аккаунты остаются `pending` без рабочих прав до назначения ролей администратором.

Telegram-бот больше не используется для регистрации, входа, паролей, привязок и действий администратора. Старые логины продолжают работать с прежним паролем; исторические идентификаторы и аудит сохраняются.

## Окружение

```env
VITE_SUPABASE_URL=https://exijfprfwmyplggayrpt.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=YOUR_PUBLIC_PUBLISHABLE_KEY
SUPABASE_URL=https://exijfprfwmyplggayrpt.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_KEY
SECURITY_AUDIT_SECRET=YOUR_RANDOM_SERVER_ONLY_SECRET
```

Ключ service_role нужен серверным API. Никогда не добавляйте его в `VITE_`. `SECURITY_AUDIT_SECRET` — необязательный отдельный ключ HMAC для псевдонимизации IP; без него используется service_role. Можно перенести прежнее значение `TELEGRAM_WEBHOOK_SECRET` в `SECURITY_AUDIT_SECRET`, чтобы сохранить сопоставимость старых хешей. Само имя переменной Telegram больше не используется.

## Активация

1. Подготовьте Google OAuth Web application в Google Cloud. Authorized redirect URI: `https://exijfprfwmyplggayrpt.supabase.co/auth/v1/callback`. Client ID и Client Secret внесите только в Supabase → Authentication → Providers → Google. Включите провайдер. Клиентские переменные для секрета Google не нужны.
2. В Supabase настройте Site URL и разрешённые Redirect URLs: production `/login` и `/login**` для query-параметров, а для разработки `http://localhost:3000/login**`. Используйте конкретные домены и HTTPS для production. SDK использует PKCE, возврат после входа допускается только на внутренний путь.
3. В Authentication включите TOTP enrollment и verification. Для кнопки «Привязать Google» включите manual identity linking. Существующий пользователь сначала входит в свой прежний аккаунт и привязывает Google в «Настройки → Безопасность». Там же можно добровольно подключить Google Authenticator. Так сохраняются UUID, роли и данные. Если Google уже связан с другим аккаунтом, автоматического переноса ролей нет.
4. Для регистрации и восстановления по email настройте SMTP и шаблоны писем Supabase. Аккаунтам со старым внутренним адресом `@telegram.supportos.invalid` письма не доставляются: они входят по прежнему логину/паролю и привязывают Google. При потере пароля/Authenticator нужна проверка личности администратором через доверенный канал и восстановление в Supabase Auth.
5. Примените `supabase/migrations/20261013102133_google_authenticator_auth.sql` **вместе с деплоем новой версии приложения**. Миграция переводит серверные проверки, RLS и критичные действия на TOTP. Не применяйте её заранее к работающей старой версии с Telegram: старый интерфейс не умеет проходить новый второй фактор.
6. После перехода удалите старый webhook в настройках Telegram и отзовите токен бота. Новое приложение не обращается к Telegram и не требует его переменных окружения. Бывшие bot endpoints возвращают 410; `/api/registration` сохраняется только для серверного выхода из сессии.

Она сохраняет требование MFA для уже защищённых аккаунтов и критичных действий, разрешая обычный вход аккаунтам без подтверждённых факторов. На production миграция применена 13 октября 2026 года.

## Серверная защита

Каждый защищённый API проверяет точный bearer через `/auth/v1/user`, затем `sub`, `session_id` и существование живой сессии. Если у пользователя нет подтверждённых MFA-факторов, обычный доступ разрешён с AAL1. Незавершённое подключение по QR не включает 2FA. Как только появляется подтверждённый фактор, требуются `aal2` в точном проверенном JWT и подтверждённый TOTP-фактор текущей живой сессии. Старый AAL1-токен не получает доступ от более позднего AAL2-подтверждения той же сессии. Истёкшая или отозванная сессия всегда закрывает доступ. RBAC читается из серверной БД; `user_metadata`, frontend store и параметры тела запроса не назначают права. Поле интерфейса `authVerified` означает успешную серверную проверку доступа, а `mfaEnabled` отдельно указывает состояние 2FA.

Существующие restrictive RLS policies применяют ту же добровольную MFA-политику: живая сессия для всех, AAL2 и живой TOTP-фактор для аккаунтов с включённой 2FA. SQL имена `telegram_session_approved`, `supportos_tg_login_state` и таблица критичных подтверждений сохранены для совместимости с применёнными миграциями и журналом; их реализация проверяет Supabase Auth и не требует Telegram. Старые bot RPC лишены прав выполнения, старые незавершённые подтверждения истекают.

Создание сотрудника, изменение ролей/доступов и завершение других сессий по-прежнему требуют нового TOTP-кода. Пользователю без 2FA показывается ссылка для её активации в настройках; модальное окно действия и экран входа не создают новые факторы. Проверенное Auth время TOTP принимается не старше 60 секунд и один раз на сессию. Сервер выдаёт разрешение на 5 минут, привязанное к UUID, сессии, действию и точному payload. На выполнение пользователь нажимает отдельную кнопку. Права, живость сессии и MFA повторно проверяются при атомарном погашении разрешения; удаление всех факторов аннулирует незавершённое разрешение.

Настройки безопасности позволяют добавить новое устройство и затем удалить старое. Последнее устройство через интерфейс удалить нельзя. Для потери всех устройств администратор проверяет личность и сбрасывает факторы в Supabase; повторное включение 2FA доступно в настройках.

## Пароли и сессии

Регистрация и reset email проходят через Supabase Auth, без собственного хранения паролей или TOTP-секретов. Recovery callback сохраняет режим смены пароля; при наличии MFA требуется второй фактор. Новый пароль содержит 12–128 символов. После изменения пароля сервер завершает все сессии, SDK очищает локальную сессию; пользователь входит заново. При ошибке завершения сессий интерфейс сообщает ошибку, не выдавая её за успешный выход.

`GET /api/accounts?action=sessions` возвращает только метаданные собственных живых сессий и признак текущей. `revoke-other-sessions` использует Auth signOut со scope `others`, проверяет фактическое удаление остальных сессий и сохраняет текущую. Выход до завершения 2FA и для pending/disabled доступен через server-confirmed local signOut. Изменение scope из тела запроса игнорируется.

Журнал сохраняет успешный вход один раз на сессию, фактически записанное изменение пароля и подтверждённые завершения сессий. Старые события Telegram остаются историческими. Неверные TOTP-коды фиксирует Supabase Auth; приложение не выдумывает собственные события отказа. В журнал не копируются пароль, секрет TOTP, токены, сырой IP или Google credentials. Для IP применяется HMAC, браузер/ОС разбираются в ограниченный набор меток.

## Проверка

Локальные unit/integration тесты проверяют QR enrollment, неверный код, безопасный Google redirect, pending-регистрацию, серверную MFA/RBAC-защиту, RLS и миграцию, одноразовые разрешения, аудит и немедленный отказ отозванным JWT. Полный OAuth требует настроенных credentials и действий владельца Google-аккаунта; фактический вход и сканирование QR выполняются пользователем после согласованного деплоя миграции и приложения.
