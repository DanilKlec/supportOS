# Регистрация через Telegram

Бот: `@GetSupportOSBot`. Прежний бот с личным именем не используется. SMTP для этого сценария не нужен.

## Пользовательский сценарий

1. На сайте пользователь выбирает логин (4–32 символа: латинские буквы, цифры, подчёркивание) и пароль (12–128 символов).
2. Сайт выдаёт ссылку на бота на 20 минут. Пользователь нажимает «Старт», сверяет логин и нажимает «Подтвердить мою заявку».
3. В той же вкладке сайта нажимает «Завершить регистрацию». Только теперь создаётся аккаунт со статусом `pending`, без ролей и разрешений.
4. Администратор видит заявку и подтверждённый Telegram ID в реестре сотрудников. Выбирает роли и подтверждает существующей атомарной операцией RBAC.
5. Далее пользователь входит по логину и паролю. Существующий вход по email и паролю сохраняется.

Пароль не передаётся Telegram и не сохраняется в sessionStorage. В sessionStorage хранится только временная заявка; после обновления страницы пароль вводится заново. При закрытии вкладки до завершения потребуется новая заявка. После завершения следует входить в существующий аккаунт.

## Хранение и ограничения

- Supabase Auth по-прежнему управляет паролями, сессиями и refresh-токенами. Для новых логинов используется внутренний адрес `<login>@telegram.supportos.invalid`. Это технический идентификатор, а не подтверждение владения реальной почтой; письма туда не отправляются. Восстановление по email для таких аккаунтов не работает — обращение к администратору, как указано на форме входа.
- Существующие аккаунты не связываются автоматически по email или Telegram username. Доказательство Telegram основано на числовом ID из защищённого webhook.
- Browser token и Telegram start token независимы; в БД только SHA-256. Telegram-ссылка не позволяет завершить заявку без отдельного browser token. Ни URL бота, ни токены заявок не следует публиковать.
- Таблица и RPC доступны только `service_role`, RLS включён, прав у `anon`/`authenticated` нет. Новая интеграция не изменяет RBAC и не даёт Support доступ к QC.
- Уникальные индексы не позволяют зарегистрировать несколько аккаунтов с одним логином или Telegram ID. Повторное завершение после частичного сбоя не меняет пароль уже созданного аккаунта. Если создание не завершилось до истечения заявки, резервирование требует проверки администратором; автоматически освобождать такой резерв нельзя без проверки отсутствия Auth-аккаунта.
- Лимит: 10 новых заявок в час на HMAC адреса подключения. На Vercel используется перезаписываемый платформой `x-vercel-forwarded-for`, локально — адрес сокета. При другом reverse proxy настройте доверенный источник IP на сервере. На публичном сайте дополнительно примените ограничения трафика платформы.
- Неподтверждённые истёкшие заявки без резервирования удаляются через сутки при следующем начале регистрации. Подтверждённые привязки сохраняются для предотвращения повторной регистрации.

## Включение

Код подготовлен локально. Миграция `20260923081810_telegram_registration` применена к проекту `exijfprfwmyplggayrpt` 23 сентября 2026 года. Проверено: RLS включён; anon/authenticated не имеют доступа к таблице или RPC; service_role имеет необходимые права. Это не означает, что webhook уже включён в Telegram или опубликован на Vercel.

1. Применить `supabase/migrations/20260923081810_telegram_registration.sql` после существующей схемы RBAC. Миграция не меняет роли и существующих пользователей.
2. В серверном окружении Vercel проекта SupportOS установить:
   - `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` — существующее серверное подключение;
   - `TELEGRAM_BOT_USERNAME=GetSupportOSBot`;
   - `TELEGRAM_BOT_TOKEN` — токен именно этого бота из BotFather;
   - `TELEGRAM_WEBHOOK_SECRET` — случайный секрет (например, 32 случайных байта в hex).
3. Опубликовать код и проверить доступность `/api/registration` на стабильном HTTPS-домене. В защите preview/deployment разрешить Telegram доступ к этому webhook; иначе платформа отклонит запрос до проверки нашего секрета.
4. В защищённом окружении запуска задать те же Telegram-переменные и `SUPPORTOS_PUBLIC_URL` (HTTPS origin без пути). Выполнить `node scripts/configure-telegram.mjs`. Скрипт сверяет бота, проверяет endpoint с секретом и затем устанавливает webhook и описание. Он не печатает токен.
5. Проверить одну реальную регистрацию и одобрение. Затем отключить публичный signup в Supabase Auth, если для новых пользователей разрешён только Telegram. Серверный admin.createUser остаётся способом создания аккаунтов; существующий вход сохраняется. Email confirmation глобально отключать не нужно.

Не помещать Telegram-токен или service-role key в `VITE_*`, в чат, в команды shell или в Git. Для локальной настройки можно использовать игнорируемый `.env`; служебные ключи должны оставаться только на сервере.

## Проверки

API-тесты: подделка webhook, чужой origin, независимые proofs, отсутствие Telegram-подтверждения, игнорирование переданных ролей/email, восстановление после сбоя и неизменность пароля, только личные чаты.
SQL-тесты на PostgreSQL (PGlite): RLS/GRANT, истечение, повторное подтверждение, уникальность привязки, идемпотентность схемы и отсутствие доступа у нового аккаунта.
UI-тесты: переход в Telegram, отсутствие пароля в хранилище, завершение только после подтверждения и восстановление временной заявки после обновления.

Полный прогон: 236 тестов в 63 файлах, TypeScript, Biome для изменённых компонентов и production build — успешно. Живая регистрация с ботом требует настройки окружения и публикации.

Supabase Security Advisor: новая таблица имеет информационное `RLS enabled, no policy` — это намеренно для server-only таблицы ([пояснение проверки](https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy)). Ранее существовавшие предупреждения: `supportos_access` доступна authenticated как SECURITY DEFINER (функция проверки собственных прав, используется RLS) и [отключена проверка скомпрометированных паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection). Эта интеграция эти настройки не меняла.

Источники: https://core.telegram.org/bots/features#deep-linking, https://core.telegram.org/bots/api#setwebhook, https://supabase.com/docs/reference/javascript/auth-admin-createuser.
