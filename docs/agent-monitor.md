# LiveChat: мониторинг агентов

Страница `/agent-monitor`, пункт Tools → Контроль агентов. Смены: 09:00–16:30, 16:00–23:00, 23:00–09:00, фиксированный GMT+3. Дата ночной смены — дата начала. Назначения сохраняются отдельно для каждой даты, агент может быть назначен на несколько смен.

## Подключение

1. В проекте `exijfprfwmyplggayrpt` схема уже применена миграцией `supportos_agent_monitor`. Для другого проекта выполните `supabase/agent-monitor.sql` в SQL Editor. Это отдельная миграция, она не требует таблиц базы знаний. Прямой доступ браузера к таблицам закрыт. SQL можно выполнить повторно.
2. Добавьте серверные переменные в Vercel → Settings → Environment Variables (для локального запуска — в `.env.local`):

```env
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_SERVER_SERVICE_ROLE_KEY
LIVECHAT_AUTHORIZATION=Basic YOUR_BASE64_ACCOUNT_ID_COLON_PAT
LIVECHAT_ORGANIZATION_ID=YOUR_ORGANIZATION_UUID
LIVECHAT_WEBHOOK_SECRET=YOUR_RANDOM_WEBHOOK_SECRET
MONITOR_COLLECTOR_SECRET=YOUR_RANDOM_COLLECTOR_SECRET
```

Для PAT заголовок Basic содержит base64 от `account_id:personal_access_token`, как в официальной инструкции LiveChat. Альтернатива — `Bearer ACCESS_TOKEN`; обновление истекающего OAuth-токена нужно организовать отдельно. PAT удобнее для первого серверного подключения. Нужен доступ `agents--all:ro` к агентам лицензии. Никогда не используйте префикс `VITE_` для этих секретов. Настройте личные аккаунты и роль `supervisor` по инструкции [Supabase Auth](auth.md). Общего пароля мониторинга больше нет.

3. Сделайте redeploy, откройте `/agent-monitor`, войдите личным аккаунтом Supabase с ролью руководителя. Кнопка «Обновить» запускает первый опрос. Неудачный LiveChat-запрос показывается в интерфейсе; запись устаревшего статуса не выдаётся за текущую. Мониторинг читает статусы, но не переключает реальный приём чатов.
4. В Developer Console LiveChat зарегистрируйте webhook `routing_status_set`:
   - URL: `https://YOUR_DOMAIN/api/agent-monitor?action=webhook`;
   - Secret key: значение `LIVECHAT_WEBHOOK_SECRET`;
   - приложение установлено на нужной лицензии, организация соответствует `LIVECHAT_ORGANIZATION_ID`;
   - для регистрации через Configuration API нужен scope `webhooks.configuration:rw` и Client ID приложения. Не требуется добавлять это право токену ежедневного чтения, если webhook регистрируется отдельно.

## Непрерывный сбор

Webhook фиксирует переключения и при закрытой странице. Дополнительно обязательно настройте опрос каждые 30–60 секунд: он подтверждает актуальность статуса, обнаруживает пропущенные уведомления и даёт исходное состояние после запуска.

На постоянно работающем сервере с Node.js 22+ задайте `MONITOR_URL=https://YOUR_DOMAIN` и `MONITOR_COLLECTOR_SECRET`, затем запустите под менеджером процессов с автоматическим перезапуском:

```sh
node --env-file=.env.collector scripts/agent-monitor-collector.mjs
```

`.env.collector` хранится только на сервере. Альтернатива — внешний планировщик, делающий каждые 30–60 секунд `POST /api/agent-monitor?action=collect` с заголовком `Authorization: Bearer MONITOR_COLLECTOR_SECRET`. Не помещайте секрет в URL. Скрипт не запускается автоматически при сборке, Vercel не исполняет постоянный цикл внутри функции.

При открытой странице опрос запускается каждые 30 секунд, чтение базы — каждые 10 секунд. Распределённая блокировка в Postgres предотвращает дублирующий опрос несколькими вкладками. Без внешнего сборщика непрерывный отчёт при закрытых страницах не гарантируется.

## Как интерпретировать отчёт

- «Принимает» = `accepting_chats`; «Выключен» = `not_accepting_chats`; «Не в сети» — только явно полученный `offline`. Отсутствующий статус остаётся неизвестным.
- Каждое наблюдение действительно максимум 90 секунд, до следующего наблюдения. Дальнейшее время считается неизвестным. Сумма всех четырёх длительностей равна прошедшей части смены.
- Начальный статус отмечается как первое наблюдение; период до него не восстанавливается задним числом.
- Время записи webhook — время получения сервером. Документированный `routing_status_set` не содержит времени события, уникального ID доставки, автора или причины. Эти данные не выдумываются. Повтор того же статуса не создаёт новую видимую смену статуса. Задержавшееся уведомление может временно устареть; следующий опрос сверяет состояние. Это операционный журнал наблюдений, не кадровый табель с гарантированным временем действия.
- Изменения расписания имеют отдельный журнал с проверенным сервером UUID личного аккаунта руководителя. Роль читается из Supabase `app_metadata`, пользовательские поля роли игнорируются.
- Длительности агрегируются в Postgres; исходные наблюдения остаются в базе. CSV выгружает сводку выбранной смены с текущими фильтрами. Журнал сначала загружает 1000 последних изменений за рабочий день; более ранние события доступны через кнопку загрузки следующей страницы.
- Данные до запуска сборщика недоступны. Не удаляйте старые наблюдения, если они ещё нужны в отчётах. Объём хранения растёт примерно на число агентов × 2880 строк в сутки при 30-секундном опросе.

## Проверка запуска

Откройте страницу, дождитесь списка, назначьте тестового агента на сегодняшнюю смену. В LiveChat измените его статус и проверьте появление события. Закройте SupportOS, измените статус ещё раз, откройте страницу — событие должно сохраниться webhook/сборщиком. Остановите сборщик и закройте вкладки на несколько минут — пропуск должен отображаться как неизвестное время. Отдельно проверьте неверный пароль, отказ обычному пользователю, выход, недействительный webhook secret и смену даты на ночную.

Локально `npm run dev` обслуживает тот же API через Vite middleware. `npm run preview` — только статическая сборка, backend там не запускается. Тесты API используют фикстуры, поэтому не обращаются к реальному аккаунту.

Документация: [routing statuses](https://platform.text.com/docs/messaging/agent-chat-api/v3.5/#list-routing-statuses), [webhooks](https://platform.text.com/docs/management/webhooks/v3.5), [registration](https://platform.text.com/docs/management/configuration-api/v3.5/#register-webhook).

Состояние на момент реализации: SQL и права проверены удалённо; реальный сбор LiveChat не запускался. В интерфейсе отдельно показаны время последнего успешного API-опроса и последнего принятого webhook. Нет новых webhook — не означает обрыв связи.


## Аналитика онлайн-агентов

Основной список, назначения и журнал показывают только агентов с подтверждённым текущим статусом «Принимает» или «Приём выключен». Статусы старше 90 секунд скрываются вместе с offline; история в базе при этом сохраняется. Дата и смена задают период аналитики, состав списка определяется текущим присутствием.

Почта отображается из идентификатора агента LiveChat, если он является email; для иных идентификаторов явно показывается ID. Поиск работает по имени и идентификатору. Сортировка доступна по времени выключенного приёма, последнему изменению и имени.

Журнал содержит время наблюдения, имя, email/ID, предыдущий и новый статус, источник. Первое доступное наблюдение и появление в сети не считаются ручным переключением. Фильтры «Только выключения» и «Только включения» показывают обнаруженные переходы on/off среди загруженных событий. Для более ранней истории используйте загрузку предыдущих событий. Автор нажатия и точное время действия LiveChat здесь не предоставляет.
