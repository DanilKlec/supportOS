# Telegram 2FA

Каждая Supabase-сессия требует отдельного подтверждения в @GetSupportOSBot. Подтверждение регистрации не заменяет подтверждение входа. Refresh access token сохраняет session_id, поэтому не вызывает новый запрос. Старые сессии автоматически не доверяются.

## Реализация

- `server/_auth.js` проверяет точный Bearer через Supabase `/auth/v1/user`, затем читает sub/session_id только из проверенного JWT. Без session_id запрос отклоняется. Проверка Telegram выполняется до RBAC для всех пользовательских API, включая `accounts?action=me`.
- `/api/registration?action=2fa-status|2fa-begin|2fa-link|2fa-cancel` использует только проверку первичной личности. Такой маршрут сохраняет лимит Vercel Hobby в 12 функций. Внешние webhook и collector сохраняют собственную аутентификацию.
- Challenge связан с user_id + session_id, TTL 5 минут. Callback содержит случайные 32 байта; в БД только SHA-256. Решение атомарно, повторные/чужие/просроченные callbacks не меняют состояние. Только личный Telegram-чат с совпадающим from.id/chat.id.
- Повторная отправка ограничена минутой и 10 запросами в час на пользователя; прежний pending становится expired. После отклонения/истечения эта сессия не получает новый challenge: нужно повторно войти с паролем. Ошибка доставки закрывает текущий flow.
- UI восстанавливает состояние с сервера, не хранит секреты Telegram в localStorage. Пока 2FA не подтверждена, не монтируются рабочие страницы. Отказ/истечение вызывают Supabase signOut с scope local; серверная проверка сессии и состояние challenge блокируют запросы независимо от браузера.
- БД проверяет существование session_id в auth.sessions и not_after. Restrictive RLS policy `telegram_2fa_gate` добавляется ко всем существующим public-таблицам с authenticated-политиками, включая знания и бинды. Таблицы 2FA доступны только service_role.
- В `supportos_private` находятся два узких SECURITY DEFINER helper для auth.sessions и RLS. Публичные управляющие RPC — SECURITY INVOKER, без EXECUTE для anon/authenticated. Права и метаданные браузера не являются подтверждением.

## Старые аккаунты

Без привязанного Telegram отображается отдельный экран привязки. После password login пользователь получает одноразовую deep link, подтверждает именно свой аккаунт в боте, затем ждёт администратора. Подтверждение бота не даёт доступа само по себе.

В реестре пользователей администратор с `users.manage` и собственной подтверждённой 2FA видит блок «Привязки Telegram». Одобрение или отказ записываются в server-only заявку (reviewed_by/reviewed_at). Самоодобрение запрещено. Telegram ID уникален; менять уже существующую привязку через этот flow нельзя. Проверенные заявки действуют 7 дней, исходные ссылки — 20 минут. После одобрения нужен отдельный login challenge.

Для самого первого администратора должна заранее существовать доверенная привязка. Не добавлять password-only bypass или автоматическое одобрение по email/username. При утрате Telegram восстановление выполняет владелец проекта через доверенный административный процесс с проверкой личности и отзывом сессий.

## Развёртывание

1. Убедиться, что минимум один активный администратор уже прошёл Telegram-регистрацию. В текущем проекте такой аккаунт найден.
2. Старые развёртывания остаются административными артефактами под Vercel Authentication. Публичным на период тестирования оставляется только домен test-auth-monitor с новым кодом. Не открывать старые URL без обновления кода.
3. Применить миграцию Telegram login 2FA к общей Supabase-базе и опубликовать код. Миграция меняет доступ ко всей базе; откат только frontend не является безопасным откатом. Не переисполнять старый schema.sql поверх установленных миграций — он пересоздаёт часть политик.
4. Существующий webhook и серверные TELEGRAM_* переменные сохраняются. Нового бота/секретов не требуется.
5. Проверить реальный вход, отказ, повторную отправку, refresh страницы, одобрение первой привязки и доступ к API до/после подтверждения.

Trusted devices не реализованы. Это собственный дополнительный фактор приложения, он не меняет Supabase JWT `aal` на `aal2`. Все будущие API и новые таблицы должны сохранять серверную/RLS-проверку 2FA.

Ссылки: [Supabase session_id и отзыв сессий](https://supabase.com/docs/guides/auth/sessions), [Telegram Bot API](https://core.telegram.org/bots/api).
